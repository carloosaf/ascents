Climbing Social Network Plan

A focused MVP for a Reddit-like climbing app where gyms act as communities, admins manage boulder problems, members post updates, and climbers record ascents against real routes.

Stack: Elixir, Phoenix, LiveView, PostgreSQL. Scaffold created with Phoenix 1.8 and official generated authentication.

Product Scope

Area MVP Decision Out of Scope Initially
Community model Gyms act as scoped communities with an owner, members, route data, posts, and moderation permissions. Cross-gym federation, global moderation teams, paid gym plans.
Climbing data Ascents are structured records connected to a user, gym, boulder problem, grade snapshot, and date. Official rankings, competitions, training plans, rope routes.
Social feed Members can publish text and media posts inside joined gyms; posts may optionally create an ascent record. Voting, awards, private messages, algorithmic feed ranking.
Media Image upload support should be planned through an S3-compatible abstraction. Video hosting is deferred. Native video transcoding, live streaming, long-term CDN strategy.

Risks

Risk Impact Mitigation
Gym impersonation Users can create official-looking gym communities before a real gym owner claims them. Allow creator-owned gyms in MVP, but include future verified_at, ownership transfer, and admin review concepts in the model.
Media cost and complexity Video upload and processing can dominate infrastructure work before the core product loop is validated. Use MinIO locally as S3-compatible object storage, support images first, and defer video processing to a later provider.
Ascent trust model Self-reported ascents are easy to fake, which weakens any stats that look competitive or official. Treat ascents as personal logs in MVP. Add verification only if rankings, competitions, or gym-certified sends become product requirements.
Grade normalization Difficulty varies by gym, wall angle, and grading scale. Cross-gym comparisons can become misleading. Support V scale and French bouldering grades as first-class options. Store the selected scale on the gym and snapshot both grade and scale on each ascent.

MVP Requirements

ID Status Requirement Acceptance Criteria
AUTH-01 Planned Users can register, log in, log out, and manage account email. Generated Phoenix authentication works; protected routes reject anonymous users; tests cover session and registration flows.
PROF-01 Implemented Users have a public climbing profile. Profile stores username, display name, optional bio, and avatar object key or URL; username is unique and used in URLs. Task 4 added profile fields, username registration support, authenticated profile editing, and username-based member pages.
UI-01 Implemented The MVP has a small application design system before feature UI work. Core components exist for buttons, links, forms, inputs, selects, textareas, alerts, badges, tabs, empty states, feed items, route cards, stat blocks, modals, and layout shells. A development-only component gallery page renders each component with normal, hover/focus, disabled, loading, empty, and error states where relevant. Implemented as a dark-first climbing social design system with tape-style grade markers, bolt-hole wall texture, route cards, feed items, stat blocks, gym headers, and /dev/components for review.
GYM-01 Planned Authenticated users can create gyms. Creating a gym stores name, slug, description, and location; the creator becomes owner through a membership record.
GYM-02 Planned Users can join/follow and leave gym communities. Community membership is unique per user and gym. It behaves like joining or following a subreddit, does not represent real-world gym membership or payment, and joined gyms appear in the user's home feed scope.
GYM-03 Planned Gym admins can manage basic gym settings. Owners/admins can edit gym metadata; regular members and anonymous users cannot.
ROUTE-01 Implemented Gym admins can create boulder problems. A problem has title, grade, color, description, active status, and optional image object key for future media integration; it belongs to exactly one gym; grade values are validated against the gym's selected grade scale.
ROUTE-02 Implemented Each gym selects a supported bouldering grade scale. Gyms support v_scale and french by default; boulder problem forms only allow grades from the gym's chosen scale.
ROUTE-03 Implemented Gym admins can archive boulder problems. Archived problems stay visible for admin review and future historical ascents, are not shown as active route options by default, and can be reactivated by gym admins.
FEED-01 Planned Members can create normal posts inside a gym. A post supports text body and optional image attachment; only members can publish; everyone allowed by visibility rules can read.
FEED-02 Planned Users can comment on posts. Comments belong to a post and user; comments can be soft-deleted for moderation without breaking thread history.
ASC-01 Planned Members can mark a post as an ascent. Creating an ascent post requires selecting an active boulder problem and creates both a post and an ascent in one transaction.
ASC-02 Planned Ascents preserve historical route data. Each ascent stores the current grade and grade scale as a snapshot so later route or gym scale edits do not rewrite the user's history.
STATS-01 Planned Users can view personal climbing stats. Stats show total ascents, ascents by grade, ascents by gym, and recent ascent timeline using structured ascent records.
MOD-01 Planned Gym admins can moderate posts in their gym. Admins can hide or soft-delete posts and comments; normal users cannot moderate content they do not own.
MEDIA-01 Planned The app supports image uploads through object storage. Local development uses MinIO; application code stores object keys and serves media through authorization-checked signed URLs, never raw binary data in PostgreSQL.
MEDIA-02 Planned Media access is secure in the MVP. Uploaded media is private by default; every media URL is short lived or proxied after checking that the requesting user can view the owning gym, post, route, profile, or ascent.

Suggested Domain Model

Entity Purpose Important Fields
users Authenticated climbers. email, username, display_name, avatar_url
gyms Community container and physical climbing gym. name, slug, description, location, grade_scale, verified_at

Phoenix Architecture

Contexts

  • Ascents.Accounts: generated auth and profiles.
  • Ascents.Gyms: gyms, memberships, admin roles.
  • Ascents.Routes: boulder problems and route media.
  • Ascents.Feed: posts, comments, feed queries.
  • Ascents.Ascents: ascent logging and stats queries.

LiveView surfaces

  • Home feed for joined gyms.
  • Gym page with posts, route list, and admin tools.
  • Boulder problem detail page with ascents and comments.
  • Create post modal with ascent mode toggle.
  • User stats page with grade, gym, and timeline filters.

Policies

  • Only gym admins create or archive boulder problems.
  • Members can post in joined gyms.
  • Users can edit their own posts for a short window.
  • Admins can moderate posts in their gyms.

Non-Functional Requirements

Area Requirement Acceptance Criteria
Security Authorization must be enforced in contexts as well as LiveViews. Tests call context functions directly and prove unauthorized users cannot mutate gyms, routes, posts, comments, or ascents.
Data integrity Critical invariants must use database constraints and changeset errors. Unique slugs, unique memberships, foreign keys, required ownership relations, and soft-delete fields are covered by migrations and tests.
Testing Each context and major LiveView flow must have focused tests. The MVP is not accepted until context tests, LiveView tests, and the generated auth tests pass with PostgreSQL running.
Accessibility Core workflows must be usable with semantic forms, labels, and keyboard navigation. Forms have labels and validation messages; buttons and links use correct elements; feed interactions do not require hover.
UI consistency Feature pages should be assembled from shared components rather than one-off CSS per screen. The component gallery is reviewed before implementing gym, route, feed, ascent, and stats screens; new visual patterns are added to the gallery before being used in feature pages.
Performance Feed and stats queries must avoid obvious N+1 loading patterns. Feed queries preload authors, gym, route, and counts in bounded queries; stats use aggregate queries rather than in-memory reduction over all rows.
Observability MVP should keep Phoenix defaults and add structured error paths around media uploads. Upload failures return user-safe messages and log actionable error details for development.

MVP Flow

1. Register User creates an account and profile.
2. Create gym Creator becomes owner/admin automatically.
3. Add problems Admin records active boulders with grades and photos.
4. Subscribe Climbers join gyms they care about.
5. Post ascent User marks a post as an ascent and selects a boulder problem.
6. View stats User sees climbs by grade, gym, date, and recent progress.

Open Decisions

Decision Default for MVP Reason to Revisit
Gym visibility Publicly readable gyms; posting requires joining the gym community. Private gyms or invite-only communities require extra access rules.
Ascent duplicates Allow multiple ascents per user and boulder problem, because climbers may repeat problems. Stats may need separate "unique sends" and "repeat sends" metrics.
Gym verification Store fields that support verification later, but do not build the review workflow in MVP. Required before marketing this as official gym software.
Grade scale Each gym chooses v_scale or french. Boulder problem grades are selected from that scale, and ascents store both grade and scale snapshots. Additional scales can be added later, but free-text grades are not the default path for MVP boulder problems.
Media access Private objects with authorization-checked signed access URLs from the MVP. Public objects may be considered later only for explicitly public assets such as marketing images or verified public gym logos.
Moderation depth Admin hide/soft-delete only. Reports, bans, rate limits, and audit logs become necessary once there are real public users.

Implementation Notes

  • Local infrastructure Plan a docker-compose.yml with PostgreSQL and MinIO. PostgreSQL backs Phoenix/Ecto; MinIO provides S3-compatible object storage for image uploads during development. Do not require either service to be running for reading this plan.
  • Design system first Build a small component gallery before feature pages. The gallery should live behind development-only routes and make visual review cheap before any gym, route, feed, ascent, or stats page depends on the components.
  • Media abstraction Keep uploads behind a small media boundary from the start. The application should not depend directly on local filesystem paths or MinIO-specific APIs outside that module. Media objects are private by default and should be exposed only through signed URLs or a Phoenix route that performs authorization before streaming.
  • Grade scales Support V scale and French bouldering grades in the MVP. Store the selected scale on each gym, validate boulder problem grades against that scale, and snapshot both grade and scale on ascents.
  • Database constraints Enforce membership uniqueness, gym slug uniqueness, and ascent uniqueness rules at the database layer instead of relying only on LiveView validation.
  • Ranking discipline Avoid global ranking in the MVP. It introduces cheating, verification, grade normalization, and moderation requirements before the core gym community loop is proven.
