Task 4 Profile Extension Plan

Extend the generated Phoenix auth user into a logged-in member profile without breaking the existing magic-link and settings flows. The first pass should require username during registration, create the data foundation, username lookup, profile edit path, and authenticated profile page; avatar uploads remain a reference field until the media boundary is implemented.

Source plan: .plans/ascents-social-plan.html. Previous implementation plan: .plans/task-3-design-system-plan.html. Target stack: Phoenix 1.8, LiveView, HEEx, Ecto, PostgreSQL.

Decision

Question Recommendation Reason
Should username be required during registration? Yes Every account should have a stable member URL from the start. The registration form should collect username together with email, and the Accounts context should enforce username format and uniqueness before sending the magic-link email.
Should avatar upload be implemented now? No upload yet Task 10 owns the media boundary and MinIO-backed private object storage. Task 4 should store an avatar_object_key or temporary avatar_url reference, render fallback initials, and avoid filesystem or object-storage code.
Should profile lookup use user IDs or usernames? Use usernames The general plan says username is unique and used in URLs. The member route should therefore be readable, for example /u/mara, while internal code continues to use user IDs and scopes for authorization.

Scope

Area Status Goal Not Included
User schema Planned Add username, display_name, bio, and avatar reference fields to users. Separate profile table, social graph fields, notification preferences, or account privacy settings.
Profile changeset and context API Planned Add explicit profile validation and scoped update functions in Ascents.Accounts. Rewriting generated email/password settings APIs or changing the login flow.
Authenticated profile editing Planned Provide an authenticated settings form so a signed-in user can update their member profile fields. Admin editing of other users, moderation tooling, or onboarding tours.
Authenticated member profile route Planned Render a basic logged-in member profile page by username with profile header, bio, avatar fallback, and placeholder stats/feed areas. Real ascent stats, gym memberships, posts, comments, or media authorization logic.

Data Model

Field Type Validation Notes
username :citext or :string Required at registration; 3-32 characters; lowercase letters, numbers, and underscores; unique. :citext is already enabled for email and simplifies case-insensitive uniqueness. If using :string, add a functional unique index on lower(username).
display_name :string Optional; max 80 characters. Use username as the display fallback when this field is blank.
bio :string Optional; max 280 characters. Keep short for MVP profile headers and feed cards. The product decision is 280 characters for this task.
avatar_object_key :string Optional; max 512 characters. Store an object key or later media reference, not raw binary data. Render initials until media access exists.

Context API

Function Purpose Critical Behavior
get_user_by_username/1 Load an authenticated member profile by username for show pages. Return nil for unknown or blank usernames. Do not expose email in templates.
change_user_profile/2 Build the profile form changeset. Return an Ecto.Changeset and let the caller convert it with to_form/2.
update_user_profile/2 Update the signed-in user's profile. Accept %Ascents.Accounts.Scope{} as the first argument, update only current_scope.user, and never accept user_id params from the browser.
profile_complete?/1 Centralize whether a user has the required profile fields. Return true when username is present. Later tasks can use this to nudge users before posting or joining gyms if needed.

Risks

Risk Impact Mitigation
Profile task is early A member profile will be mostly empty before gyms, posts, routes, ascents, and stats exist. Keep the UI intentionally simple: profile header, bio, avatar fallback, and clearly reusable placeholder sections. Do not fake real stats in production code.
Username migration conflicts with existing users Adding a non-null unique username immediately can fail in any database with preexisting auth users. Either keep username nullable until profile completion, or backfill deterministic usernames in the migration before adding a non-null constraint. Because this app is early, nullable plus profile-complete checks is the safer first pass.
Email leaks into profile UI Generated auth users are email-first, so careless templates may expose private account identifiers. Profile templates must use username, display name, bio, and avatar fallback only. Tests should assert the email is not rendered.
Avatar field becomes media architecture Implementing uploads now duplicates or undermines the future media boundary. Store only a reference field and render initials until Task 10 defines signed URLs and object storage access.
Route ordering conflict A broad username route could accidentally capture existing routes if placed poorly. Use a namespaced member route such as /u/:username instead of /:username.

Acceptance Criteria

  • Data model is accepted when Users have profile fields, username uniqueness is enforced at the database and changeset layers, and existing auth tests still pass.
  • Profile editing is accepted when A signed-in user can update their own username, display name, bio, and avatar reference through an authenticated settings route, and anonymous visitors are redirected away from that route.
  • Member profile is accepted when /u/:username renders a profile only for authenticated visitors, uses Layouts.app with current_scope, redirects anonymous visitors to login, and never renders the user's email.
  • Tests are accepted when Fixture helpers create profile-ready users; context tests cover validation and uniqueness; web tests cover authenticated rendering, settings updates, anonymous redirects, and not-found behavior.
  • Task 4 is complete when mix precommit passes after implementation.

Open Questions

  • Bio length The plan recommends a short bio limit, but the product decision The product decision is 280 characters so profiles remain feed-card friendly.
  • Username reservation Do not reserve special usernames in this task. The /u/:username namespace is enough to avoid route collisions for the MVP.
  • Profile completion timing Username is required during registration. Display name, bio, and avatar reference can still be edited later from settings.

Implementation Notes

  • Do not use @current_user Templates should derive the user from @current_scope.user when needed, following the generated auth model.
  • Use form assigns Profile templates should use to_form/2 in the LiveView and reference fields as @profile_form[:username], never as changeset fields.
  • Keep visible data intentional The member profile page should not render email, auth state, token state, or settings links unless the viewer is the profile owner.
  • Reuse Task 3 components Use the app shell, buttons, empty states, stat blocks, and avatar style from AscentsWeb.ProductComponents before adding new one-off profile markup.
