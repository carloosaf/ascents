Tasks 1 and 2 Implementation Plan

A focused execution plan for the first implementation pass: define local infrastructure for PostgreSQL and MinIO, then establish a clean Phoenix project health baseline before domain work starts.

Source plan: .plans/ascents-social-plan.html. Target stack: Elixir, Phoenix 1.8, LiveView, PostgreSQL, MinIO-compatible object storage.

Scope

Task Status Goal Not Included
1. Local services definition Implemented Add a reproducible local service definition for PostgreSQL and MinIO, plus clear environment variable documentation for the Phoenix app. Production infrastructure, object lifecycle policies, CDN configuration, or starting long-running services during the plan update.
2. Project health baseline Implemented Prove the generated Phoenix app compiles, formats cleanly, and uses a predictable local PostgreSQL configuration for tests. Feature contexts, LiveViews, design system work, media upload implementation, or schema changes beyond configuration fixes.

Target Files

Create

docker-compose.yml

Define local PostgreSQL and MinIO services, named volumes, stable ports, health checks, and credentials intended only for development and test environments.

Update

README.md

Document how to validate the compose file, start local services, run setup, and execute the health baseline commands.

Review

config/*.exs

Check database connection settings and environment variable names. Keep Phoenix-generated conventions unless they conflict with the local service names or test database requirements.

Review

mix.exs

Confirm the existing mix precommit alias is the final verification command and do not add dependencies for this step.

Service Design

Service Local Defaults Purpose Health Check
postgres Port 5432, user postgres, password postgres, database ascents_dev. Back Phoenix development and test workflows through Ecto. Use pg_isready against the configured local database user.
minio API port 9000, console port 9001, access key minioadmin, secret minioadmin. Provide S3-compatible private object storage for future image upload work. Use MinIO's live health endpoint on /minio/health/live.

Execution Steps

1. Inspect config Read config/dev.exs, config/test.exs, and mix.exs before changing files.
2. Add compose file Create docker-compose.yml with PostgreSQL, MinIO, volumes, ports, credentials, and health checks.
3. Document setup Update README.md with local services and baseline verification commands.
4. Validate compose Run docker compose config to catch YAML or service definition errors.
5. Run baseline With PostgreSQL available, run format, compile, tests, and mix precommit.
6. Record blockers If Docker or PostgreSQL is unavailable, report exact commands run and the blocking error.

Verification Matrix

Check Command Expected Result Required For
Compose syntax docker compose config Prints normalized configuration and exits successfully. Task 1 acceptance
Format baseline mix format --check-formatted No formatting changes are required. Task 2 acceptance
Compile baseline mix compile --warnings-as-errors Application compiles without warnings. Task 2 acceptance
Test baseline mix test Generated auth, controller, and account tests pass with PostgreSQL running. Task 2 acceptance
Final gate mix precommit Compile, dependency hygiene, format, and tests all pass. Done criteria

Risks

Risk Impact Mitigation
Port conflicts Local PostgreSQL or MinIO may already be running on the default ports. Keep defaults simple in docker-compose.yml, and document changing host ports as the local escape hatch.
Database mismatch Phoenix test config may target credentials that do not match the compose service. Align compose defaults with Phoenix-generated repo settings where possible, and only edit config when the baseline commands prove it is necessary.
Docker unavailable Compose validation or service startup cannot complete in the current environment. Still commit a syntactically simple compose file, run every non-Docker check possible, and report Docker as the remaining blocker.
MinIO bucket setup Future upload work needs a bucket before images can be stored. Keep bucket creation documented for the media task instead of adding custom startup scripting in Task 1.

Acceptance Criteria

  • Task 1 is accepted when docker-compose.yml defines PostgreSQL and MinIO with named volumes, documented credentials, stable local ports, and health checks; docker compose config succeeds.
  • Task 2 is accepted when The generated Phoenix app passes formatting, compile, and test checks against the local PostgreSQL service, and the final mix precommit alias passes.
  • Documentation is accepted when README.md explains local service startup, setup, health checks, and the commands needed before moving to Task 3.

Implementation Notes

  • Use generated conventions first Keep Phoenix and Ecto configuration close to the generated defaults. The compose file should adapt to the app unless tests show the app config needs correction.
  • No extra HTTP dependencies Future object storage calls should use the already included Req library or a later deliberately chosen storage boundary. Do not add HTTPoison, Tesla, or Erlang :httpc usage.
  • No feature routes yet Tasks 1 and 2 do not add controller routes or LiveViews, so no authentication routing changes are needed in this pass.
  • Move to Task 3 only after baseline The component gallery and visual system should start from a clean compile and test baseline so later UI failures are attributable to new work.
