Task 7 Gym LiveViews Plan

Build the authenticated gym community UI layer for creating gyms, viewing gym pages, editing gym settings, and joining or leaving gym communities, plus the first owner/admin member-management workflow, using the existing Ascents.Gyms context and Task 6 authorization helpers.

Source plan: .plans/ascents-social-plan.html. Prior implementation plans: .plans/task-5-gym-context-plan.html and .plans/task-6-authorization-helpers-plan.html. Target stack: Phoenix 1.8, LiveView, generated auth scopes, Tailwind v4.

Task Boundary

In scope
  • Create a new AscentsWeb.GymLive namespace for gym pages.
  • Add LiveViews for gym index, new gym, show gym, edit settings, and member management.
  • Wire create, join, leave, update, member removal, and role changes through Ascents.Gyms.
  • Use current_scope throughout and pass it into <Layouts.app>.
  • Add LiveView tests using stable element IDs for form and membership actions.
Out of scope
  • No boulder problem management UI; that belongs to a route/problem task.
  • No feed, post, comment, ascent, or media upload workflows.
  • No invitations, pending requests, banning, ownership transfer, or verification review.
  • No public search ranking beyond a deterministic gym list.

Decisions

Question Decision Why it matters
Should gym show pages be public? Yes, read-only public A public gym page makes community discovery possible. Anonymous users can view gym metadata but cannot join, leave, create, or edit without logging in.
Should the gym index be public? Yes Gyms.list_gyms/0 is already unscoped and deterministic. A public index fits discovery while mutation remains protected by authenticated routes and context checks.
Should users choose slugs during creation? No Task 5 intentionally generates slugs from gym names. The new form should collect name, description, location, and grade scale only, then navigate to /gyms/:slug.
Should owners be allowed to leave their own gym? Use context result Gyms.leave_gym/2 already rejects :only_owner. The UI should surface that as a clear flash message rather than hiding it with special template logic.
Should task 7 include owner/admin role workflows? Yes, basic member management Add a protected member-management page for the existing role model. Owners and admins can view gym members, promote or demote members among admin, mod, and member, and remove non-owner memberships. Owner transfer stays out of scope because the current context protects the last owner and no transfer rule has been designed yet.

Route And Auth Placement

Route Scope and pipeline Why
live "/gyms", GymLive.Index Plain browser scope: scope "/", AscentsWeb with pipe_through :browser. Listing gyms is read-only and works with or without authentication. The browser pipeline still assigns current_scope through :fetch_current_scope_for_user.
live "/gyms/:slug", GymLive.Show Plain browser scope: scope "/", AscentsWeb with pipe_through :browser. Public read-only gym pages support discovery. Authenticated users see join, leave, and settings controls based on current_scope and capability helpers.
live "/gyms/new", GymLive.New Authenticated scope: scope "/", AscentsWeb with pipe_through [:browser, :require_authenticated_user]. Gym creation mutates data, creates an owner membership, and must use the generated auth current_scope.
live "/gyms/:slug/settings", GymLive.Edit Authenticated scope: scope "/", AscentsWeb with pipe_through [:browser, :require_authenticated_user]. Gym settings are mutable and must be guarded by Gyms.can_update_gym?/2. The context must still reject unauthorized updates if a route is misconfigured.
live "/gyms/:slug/members", GymLive.Members Authenticated scope: scope "/", AscentsWeb with pipe_through [:browser, :require_authenticated_user]. Viewing and changing member roles exposes community membership state and mutates authorization-sensitive data. The LiveView should require Gyms.can_update_gym?/2 or a dedicated Gyms.can_manage_members?/2 helper before rendering controls.

Every LiveView template must begin with <Layouts.app flash={@flash} current_scope={@current_scope}>. Route definitions should be added inside the existing AscentsWeb scopes without manually aliasing route modules.

UX Requirements

  • Use the existing dark climbing social visual language from the component gallery and profile pages.
  • Use imported core inputs with <.input field={@form[:field]} ... /> for all form fields.
  • Give key elements stable IDs: gyms-index, gym-new-form, gym-show, gym-join-button, gym-leave-button, gym-settings-link, gym-settings-form, gym-members-link, and gym-members-table.
  • Represent the gym's selected grade scale in readable copy: V scale or French bouldering.
  • Do not expose slug editing in creation, settings, or member-management screens.
  • Use a compact table or list for members with explicit role controls and disabled owner-protected actions.
  • Include empty states for routes, feed posts, and recent ascents, but do not implement those workflows in this task.
  • Use subtle hover and focus transitions, but avoid external scripts, inline scripts, or new CSS bundles.

Implementation Flow

1. Router Place public and authenticated routes in the correct existing scopes.
2. Shared Helpers Add small private LiveView helpers for scope loading only if needed; avoid premature components.
3. Index Render gym cards from Gyms.list_gyms/0 and link to show pages.
4. New Form Build validation and submit events around to_form/2 and Gyms.create_gym/2.
5. Show Actions Assign membership state and wire join/leave events with flash feedback.
6. Settings Gate edit access with Gyms.can_update_gym?/2 and route unauthorized users back to the gym page.
7. Members Add owner/admin member-management APIs and a protected members LiveView for role updates and member removal.
8. Tests Add LiveView tests using element selectors rather than raw HTML assertions.
9. Verify Run mix precommit and fix compile, format, and test failures.

Risks

Risk

Manual session scope loading

Existing profile LiveViews reconstruct current_scope from the session token. Best path for task 7: add a small reusable LiveView helper or on_mount hook in AscentsWeb.UserAuth if it fits the existing auth module, then use it across all new gym LiveViews. Keep the API compatible with generated auth and always assign current_scope.

Risk

Public routes with member actions

A public show page must never assume @current_scope.user exists. All membership controls should be conditional and all mutating events should re-check authenticated scope before calling the context. Join and leave should either redirect anonymous users to login or show a login link instead of rendering buttons.

Risk

Slug changes are not supported

The current update path does not accept slug edits. Settings UI must not expose slug editing. If a future task adds slug editing, it needs redirect behavior, conflict handling, and old URL strategy.

Risk

Role workflows touch authorization state

Task 7 should include the basic member-management route and UI because owners/admins need a real workflow for the roles added in Task 6. Keep the context as the source of truth: prevent unauthorized role updates, reject invalid roles, and preserve at least one owner so the gym cannot become ownerless.
