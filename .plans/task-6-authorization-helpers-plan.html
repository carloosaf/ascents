Task 6 Authorization Helpers Plan

Add a small, explicit authorization surface for gym community roles so future gym, route, feed, ascent, and moderation code can ask clear questions like "can this scope manage this gym?" without duplicating role checks in LiveViews.

Source plan: .plans/ascents-social-plan.html. Prior task: .plans/task-5-gym-context-plan.html. Target files: lib/ascents/gyms.ex, test/ascents/gyms_test.exs, and gym fixtures if needed.

Task Boundary

In scope
  • Expose role and capability helpers in Ascents.Gyms.
  • Use current_scope as the primary public API input.
  • Keep authorization enforced in context functions such as update_gym/3.
  • Add focused context tests for owner, admin, mod, member, non-member, and anonymous inputs.
Out of scope
  • No Gym LiveView routes or templates; those belong to task 7.
  • No promotion, demotion, invitation, banning, or transfer workflow.
  • No global admin or site staff authorization model.
  • No policy library dependency unless the authorization surface grows later.

Route And Auth Placement

Task 6 should not add routes. When task 7 consumes these helpers, gym creation, gym editing, join, and leave pages should be placed inside a router scope that pipes through [:browser, :require_authenticated_user] because those workflows mutate user-owned or membership-scoped data. Public read-only gym pages can stay in the plain :browser pipeline if we intentionally allow anonymous viewing; they will still receive current_scope from :fetch_current_scope_for_user.

LiveViews added later must render through <Layouts.app flash={@flash} current_scope={@current_scope}> so generated auth assigns are available consistently. Context functions should continue to reject unauthorized mutation even if a UI route is misplaced.

Proposed Helpers

Helper Meaning Allowed roles
member?/2 User belongs to the gym community and may see member-only controls. owner, admin, mod, member
admin?/2 User can manage gym metadata and future route resources. owner, admin
moderator?/2 User can perform future moderation actions. owner, admin, mod
owner?/2 User has owner-only capabilities such as future transfer or deletion rules. owner
can_update_gym?/2 Explicit capability wrapper used by update_gym/3. owner, admin
can_manage_routes?/2 Future route context gate for creating, editing, and archiving boulders. owner, admin
can_moderate_gym?/2 Future feed/comment moderation gate. owner, admin, mod
can_post_in_gym?/2 Future feed/ascent posting gate. owner, admin, mod, member

Implementation Steps

  1. Add module attributes or private role lists in Ascents.Gyms for admin, moderator, and member capability groups.
  2. Add public helpers that accept %Ascents.Accounts.Scope{} and %Ascents.Gyms.Gym{}, returning booleans for invalid, anonymous, or non-member inputs.
  3. Keep lower-level user overloads private unless tests or fixtures need them; this keeps app code aligned with generated auth's current_scope model.
  4. Replace the private can_update_gym?/2 implementation with the public scope-aware capability while preserving creator-owner behavior through the owner membership.
  5. Add a fixture helper for role-specific memberships only if direct test setup becomes noisy. Prefer using Repo.update! in tests sparingly if there is no product workflow for role assignment yet.
  6. Run mix precommit after implementation and fix any compile, format, or test failures.

Risks And Questions

Risk

No role-management workflow yet

Tests for admin and mod roles will need direct fixture/database setup because the product does not yet expose promotion or demotion actions. That is acceptable for task 6, but it means tests are proving intended policy rather than a complete user workflow.

Risk

Creator versus owner source of truth

Decision: remove creator_id from the gym model and make the owner membership the source of truth. Task 5 already creates that membership transactionally, and future ownership transfer should update membership roles rather than a separate creator field.

Decision

Should admins edit gym metadata?

Yes. admin users can update gym metadata alongside owners. The public can_update_gym?/2 helper should reflect that policy and update_gym/3 should use it.

Decision

What can mods post?

Moderators can post. can_post_in_gym?/2 should allow owner, admin, mod, and member roles.
