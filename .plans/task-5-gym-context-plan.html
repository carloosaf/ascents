Task 5 Gym Context Plan

Add the first gym domain boundary: gyms as communities, memberships as subreddit-style join records, and transactional owner assignment when a logged-in user creates a gym. A membership means "I follow or participate in this gym community"; it does not represent payment, commercial subscription, or a real-world gym membership. This task should produce reliable schemas, migrations, context APIs, fixtures, and tests before any gym LiveView pages are built.

Source plan: .plans/ascents-social-plan.html. Previous implementation plan: .plans/task-4-profile-extension-plan.html. Target stack: Phoenix 1.8, Ecto, PostgreSQL, generated auth scopes.

Decision

Question Recommendation Reason
Should Task 5 add gym LiveViews? No The general plan separates Task 5 Gym context from Task 7 Gym LiveViews. Keep this pass focused on migrations, schemas, context functions, and tests so the data model is stable before UI workflows depend on it.
What does a gym membership mean? Community join Treat it like joining or following a subreddit. It controls feed scope, posting eligibility, and community roles inside the app only. It must not imply the user pays the gym, has a real membership at the physical facility, or receives any offline access rights.
Should gym creation require an authenticated scope? Yes Every gym community needs a creator and owner join record. Public context functions that mutate gyms or memberships should accept %Ascents.Accounts.Scope{} first and derive the acting user from current_scope.user.
Should the MVP allow unverified gyms? Yes, with warning The general plan calls out gym impersonation as a risk but still allows creator-owned gyms in the MVP. Add verified_at now as a nullable future hook, but do not build claim review or ownership transfer flows in this task.
Should slugs be entered manually or generated from names? Generate by default A generated slug keeps create flows simple and gives Task 7 a readable URL target. Accept an explicit slug only from trusted server-side code or admin paths later; do not let arbitrary browser params override a normalized slug in the initial create path.

Data Model

Table Field Type Validation and Constraints
gyms name :string Required; 2-120 characters; trimmed before slug generation.
gyms slug :string Required; lowercase letters, numbers, and hyphens; unique index. Generate from name and add a collision suffix when needed.
gyms description :string Optional; max 500 characters for MVP gym headers.
gyms location :string Optional; max 160 characters. Do not model full postal addresses until search, maps, or verification require it.
gyms grade_scale :string Required; default v_scale; allow only v_scale and french for now.
gyms creator_id references(:users) Required foreign key. Set from current_scope.user, never from cast params.
gyms verified_at :utc_datetime Nullable future hook for official gym verification. No MVP logic should depend on it yet.
gym_memberships user_id, gym_id references Required foreign keys with a unique composite index on [:user_id, :gym_id].
gym_memberships role :string Required; default member; allow owner, admin, mod, and member. Add a database check constraint if the migration style stays simple.
gym_memberships joined_at :utc_datetime Required; set server-side during create. Useful for future sorting and community join history without adding an audit table.

Context API

Function Purpose Critical Behavior
change_gym/2 Build changesets for future create and edit forms. Return an Ecto.Changeset. Do not require a scope for non-mutating form preview work.
create_gym/2 Create a gym and owner community membership. Accept current_scope first, require a signed-in user, generate a slug, insert the gym and owner community join record in one Ecto.Multi transaction, and return errors as changesets where possible.
update_gym/3 Update gym metadata. Accept current_scope, the gym, and attrs. For Task 5, allow the creator or owner membership to update; Task 6 can replace the private check with explicit capability helpers.
get_gym!/1 Load a gym by ID for internal operations and tests. Preload creator or memberships only when the caller needs them. Avoid broad default preloads that hide N+1 problems later.
get_gym_by_slug/1 Load a gym for future slug-based pages. Return nil for blank or unknown slugs. Normalize slug input before querying.
list_gyms/1 Support future browse and admin surfaces. Keep the first version deterministic, such as alphabetical or newest-first ordering. Do not add full text search yet.
join_gym/2 Join or follow a gym community for the signed-in user. Accept current_scope first. Create a member role join record, enforce uniqueness in the database, and surface duplicate joins as a predictable error instead of crashing.
leave_gym/2 Leave or unfollow a gym community. Do not allow the only owner to leave without a transfer path. Return a domain error that Task 7 can render cleanly.
get_membership/2 Check whether a user belongs to a gym. Return the membership or nil. This is enough for Task 5 tests and gives Task 6 a small base for capability checks.

Risks

Risk Impact Mitigation
Gym impersonation Users can create official-looking gym communities before the real gym owner claims them. Keep gyms creator-owned and visibly unverified for now. Store verified_at as a future hook, but avoid UI claims that imply official ownership until a verification flow exists.
Weak ownership invariant If the only owner can leave, a gym can become impossible to administer. Block leaving when the user is the only owner. Ownership transfer can be added when admin settings are implemented.
Slug race conditions Two users creating gyms with the same name at the same time can collide even if the application checked first. Rely on a unique database index and retry slug generation once or return a clean changeset error. Do not trust application-only uniqueness checks.
Role model churn Owner, admin, mod, and member roles may be too much before the UI can expose them. Store the small role vocabulary now because later tasks need admin and moderation boundaries. Keep behavior minimal until Task 6 and Task 7.
Authorization spread Adding ad hoc role checks in Task 5 can make Task 6 harder to centralize. Use small private checks only where needed for context safety, then promote them into explicit authorization helpers in Task 6.

Acceptance Criteria

  • Data model is accepted when Gyms and memberships exist with foreign keys, unique slugs, unique user/gym memberships, role validation, and a nullable verification hook.
  • Gym creation is accepted when A signed-in user's scope creates a gym and exactly one owner community membership transactionally, with no browser-controlled creator_id or user_id assignment.
  • Community memberships are accepted when A signed-in user can join/follow and leave/unfollow gym communities, duplicate joins are rejected, and the only owner cannot leave.
  • Tests are accepted when Context tests cover create, update, join, leave, duplicate membership prevention, slug uniqueness, invalid roles, and scoped mutation behavior.
  • Task 5 is complete when mix precommit passes after implementation.

Open Questions

  • Membership terminology The code can use gym_memberships, but user-facing copy should prefer join, joined, follow, or community member. Avoid "subscription" unless it is clearly Reddit-style and never paid.
  • Unverified gym creation The plan allows any signed-in user to create a gym. This is fast for MVP learning, but it carries real impersonation risk if the app is shared outside a trusted test group.
  • Location shape The plan keeps location as free text. If map search, distance filtering, or real-world gym verification is near-term, this should become structured address fields or a separate location model before public data accumulates.
  • Slug mutability The plan recommends generated slugs and leaves slug editing out of Task 5. Changing slugs after launch requires redirects or stable IDs in URLs, so the product should decide before public gym pages are indexed or shared.
  • Owner leave behavior The plan blocks the only owner from leaving. If you prefer abandoned gyms to be deleted instead, that is a product decision with data loss implications and should be explicit.

Implementation Notes

  • Use generated auth scopes Mutating context functions should accept current_scope first and use current_scope.user; do not introduce @current_user assumptions.
  • Keep user IDs out of casts Fields such as creator_id, membership user_id, and owner role assignment are programmatic security decisions, not browser form params.
  • Use database constraints Slug uniqueness, membership uniqueness, foreign keys, and role validity should be enforced by the database and surfaced through changeset constraints where practical.
  • Preload intentionally Preload creator or membership associations only for functions whose callers need them. Future templates must not depend on lazy association access.
  • Do not add HTTP clients This task has no external HTTP work. If future gym verification calls an external API, use the existing Req dependency.
