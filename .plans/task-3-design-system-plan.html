Task 3 Design System and Component Gallery Plan

Build the product UI foundation before gym, route, feed, ascent, and stats pages are implemented. The goal is a small, controlled Phoenix component system with a development-only gallery that makes visual review cheap and keeps feature work from turning into one-off markup.

Source plan: .plans/climb-social-plan.html. Previous implementation plan: .plans/tasks-1-2-implementation-plan.html. Target stack: Phoenix 1.8, LiveView, HEEx, Tailwind CSS v4.

Decision

Question Recommendation Reason
Use DaisyUI as the application design system? No for new product UI The project instructions explicitly say to manually write Tailwind-based components instead of using DaisyUI. More importantly, Climb needs domain-specific feed, route, grade, ascent, and gym-management surfaces; those will feel generic if the app is assembled mostly from preset Daisy classes.
Can the generated DaisyUI setup remain temporarily? Yes, as migration scaffolding Phoenix generated this app with Daisy-flavored defaults in CoreComponents and app.css. Task 3 can replace app-facing component markup first, then remove or neutralize unused Daisy dependencies after the gallery proves no product component depends on them.
Is a full custom system too much? Build a small one This is not a large design-system project. The first pass should define only the primitives and product components needed for the MVP, keep them in Phoenix components, and document them by rendering real examples in the gallery.

Route Placement

Route Scope and Pipeline Why
/dev/components Inside the existing if Application.compile_env(:climb, :dev_routes) block, in the scope "/dev" that uses pipe_through :browser. The gallery is a development tool, not a product surface. The :browser pipeline still fetches current_scope, session, flash, CSRF protection, and the root layout. It should not require authentication because unauthenticated, authenticated, empty, and error states all need to be visible during design review.

Visual Direction

Tone

Playful climbing community

The app should feel social-first, playful, and community-driven: more like a climbing club feed than a gym operations dashboard. Admin tools still need to be clear and efficient, but the default product feeling should be people, routes, sends, comments, and shared gym activity.

Palette

Dark social base, bold route accents

Treat dark mode as the primary design target. Use deep neutral surfaces, readable off-white text, and restrained borders, then reserve strong color for grade pills, route tape, active actions, and social feedback. Light mode can exist, but it should be derived after the dark experience feels right.

Shape

Compact and readable

Cards should stay at 8px radius or less. Feed and admin surfaces should be dense enough to scan repeatedly, with clear section rhythm and no card-inside-card layouts.

Motion

Small feedback only

Use subtle transitions for hover, focus, loading, and pressed states. Avoid decorative motion until there is a clear product purpose.

Product Experience Defaults

Decision Default Design Consequence
Primary product mode Social tool Lead with home feed, gym activity, route posts, comments, member identity, and ascent celebrations. Management surfaces should support the community loop without becoming the visual center of the app.
Mood Playful and community-driven Use friendly copy, visible member avatars, lively grade chips, small celebratory states, and softer interaction details. Keep the layout polished enough to avoid feeling childish.
Media balance 50% images, 50% text/data Feed items and route cards should pair meaningful photos with readable captions, comments, grade metadata, and gym context. Avoid both photo-only masonry and text-heavy forum layouts.
Primary theme Dark mode first Design and review the gallery in dark mode first. Use light mode as a supported alternate theme after dark surfaces, contrast, hover states, media treatment, and validation states are proven.
Grade treatment Bold grade markers Grades should be immediate visual anchors: strong pills, swatches, or tape-like tags on route cards and ascent posts. They can carry more color and contrast than normal metadata.

Reference-Inspired Design Principles

The reference images point toward a polished editorial-product language: generous white space, strong image-led modules, soft panels, crisp typography, and a few high-energy accents. Climb should borrow that layout confidence without copying the fashion, fitness, or AI startup color palettes directly.

Principle How to Apply It to Climb What to Avoid
Editorial grid Use asymmetric but orderly layouts: a wide feed column, compact side panels for gym stats or active problems, and image-forward route cards. Let modules vary in span and emphasis while staying aligned to a clear grid. A uniform wall of identical cards, nested cards, or dashboard panels that all have the same visual weight.
Soft product surfaces Prefer off-white page backgrounds, white panels, subtle borders, quiet shadows, and 8px-or-less radii. Panels should feel tactile but still practical for repeated feed and admin use. Heavy drop shadows, glossy gradients, large rounded blobs, or decorative backgrounds that compete with climbing content.
Image-led hierarchy Give route photos, gym cover images, and ascent media meaningful space, but pair each image with enough text and metadata to make the community context obvious. Use consistent aspect ratios so the feed remains stable while still feeling visual and social. Tiny thumbnails for content that should be inspected, dark overlays that make climbing holds hard to see, or image crops that hide the route.
Confident type scale Use large, clean headings for page identity and compact labels for metadata such as grade, wall, setter, gym, and climb date. Keep letter spacing at zero and avoid viewport-scaled text. Marketing-sized headings inside small cards, negative letter spacing, or dense metadata that wraps unpredictably on mobile.
Accent discipline Use one vivid action accent, one playful community accent, and bold route grade treatments as domain-specific anchors. Most large surfaces should remain neutral so grades, holds, people, and user media stand out. Coloring every panel, relying on a single hue family, or letting neon accents dominate reading-heavy screens.

DaisyUI Transition Plan

1. Inventory usage Search for Daisy classes such as btn, input, alert, card, navbar, and table.
2. Replace app shell Remove Daisy classes from Layouts.app and the theme toggle while preserving behavior.
3. Replace core components Restyle .button, .input, .flash, .table, and .list with explicit Tailwind classes.
4. Build product components Add route, feed, grade, gym, and stat components using realistic sample data.
5. Render gallery Add /dev/components and check desktop and mobile widths.
6. Remove dependency later Once no templates depend on Daisy classes, remove Daisy plugin imports from app.css in a separate cleanup pass.

Execution Steps

  1. Inspect all current Daisy class usage and decide which generated components need compatibility-preserving restyles.
  2. Create or update component functions before changing feature templates, so the gallery can be the source of truth.
  3. Add the development-only LiveView route under the existing /dev browser scope and explain that placement in the implementation summary.
  4. Convert the generated home/auth surfaces only enough to avoid visual clashes with the new shell. Do not build real product workflows in Task 3.
  5. Add focused tests that prove the gallery route is available in development routes and that key component IDs/selectors render.
  6. Run mix precommit after all Task 3 changes and fix any compile, formatting, or test failures.

Risks

Risk Impact Mitigation
Overbuilding the design system Task 3 could become a design project instead of an implementation foundation. Build only the components needed by the MVP plan and add more only when a later feature task proves the need.
Daisy classes lingering in generated auth pages The app may look inconsistent even after new product components are styled. Restyle shared components first so generated auth templates improve without broad page rewrites.
Dev route accidentally exposed Internal component examples could be reachable in production. Place the route only inside the existing :dev_routes compile-time block and include a route test or compile-time check.
Current scope assign errors LiveView templates may fail if current_scope is not available or not passed to Layouts.app. Keep the gallery in the :browser pipeline and begin LiveView templates with <Layouts.app flash={@flash} current_scope={@current_scope}>.

Acceptance Criteria

  • Design decision is accepted when New app-facing UI does not depend on Daisy component classes, and any remaining Daisy usage is documented as generated legacy styling to be removed after replacement.
  • Gallery is accepted when /dev/components renders core and product components with realistic sample data, normal states, empty states, loading states, disabled states, and validation states.
  • Components are accepted when Buttons, forms, inputs, alerts, badges, tabs, empty states, modal shell, route cards, feed items, stat blocks, and app shell are reusable Phoenix components or clearly reusable HEEx patterns.
  • Routing is accepted when The component gallery is inside the development-only /dev browser scope, with no authentication requirement and no production route exposure.
  • Task 3 is complete when mix precommit passes after implementation and the gallery has been manually reviewed at desktop and mobile widths.

Implementation Notes

  • Use Phoenix components as the boundary The user of the codebase should call <.button>, <.input>, and Climb-specific helpers rather than remembering long repeated class strings in every feature template.
  • Keep Tailwind explicit Use Tailwind utility classes directly in HEEx components and small custom CSS only where utilities are not the right tool. Do not use @apply.
  • Use icons through <.icon> Use the generated hero icon component from CoreComponents. Do not import Heroicons modules or add separate icon dependencies.
  • Prefer boring structure and specific details The unique feel should come from climbing-specific components, spacing, typography, route colors, and interaction states, not from decorative backgrounds or generic UI kits.
